# Spec: Tracking outstanding asynchronous work for Reel

## Context
The `reel` CLI and the browser UI both observe the ever-shifting signal that represents the backgammon timeline. The signal convulses whenever the table is touched, the cursor crawls through new touches, the perspective cache resolves, or timer-driven catch-up loops fire. We already filtered the noisy emissions so downstream subscribers no longer see every internal stumbling step. A second problem remains: even after the noise is tamed, observers still cannot tell whether any work is outstanding. We now need a manager that keeps tabs on every request so that once the register reads empty, anyone using the signal—especially `src/libs/reel/cli.js`—knows the world has truly stopped moving.

## Mental model
1. **Table subscription & touches:** The shell seeds `$table` from Supabase and subscribes to table updates over `supabase.channel('db-messages')`. Each change causes `getTouches` to fetch the latest touches and updates the timeline via `r.addTouches`, which recalculates cursor and refreshes the derived state.
2. **Timer catch-up:** A 1s timer (`timer(1000, Date.now)`) looks at the timeline and, if the cursor is behind, calls `r.forward` until `cursor.max` is reached. Every tick may trigger operations (timeline swaps, perspective lookups) that issue network requests.
3. **Perspective loading:** `$state` merges timeline, table, seating info, and other gates. It inspects the current and anticipated `ats` to fetch `getPerspective` for each one. Those fetches, together with `getLastMove`, emit promises that resolve later and mutate the timeline when each response arrives.
4. **Application actions:** Dispatching commands (`$.dispatch`) stops the timer and, when moving/undoing, calls Supabase functions (`move`, `undo`). Those backend calls mutate the table, which feeds back into the same chain of touch/timer/perspective activity.
5. **Outstanding work register:** Each of the above asynchronous touch points produces an external request. The CLI (and any external subscriber) does not need to ignore their intermediate states; it only needs to know whether any of those requests are still in flight.

6. **Workboard-driven readiness:** We already have a `$ready` signal and the `can` helper that builds `finally` guards around user-issued commands. The intent is correct, but the implementation should rest on a `$workboard` atom instead of hand-toggling `$ready`. All asynchronous actors—Supabase table touches, the current player’s move or do-over commands, timer catch-up steps, perspective fetches, and any downstream dominoes they trigger—record work on the board before sending requests and clear it in resolve/reject handlers. Reject still settles the ticket because failure completes the work; `$error` captures the payload for inspection. `$ready` simply becomes a derived signal: it is `true` when the board has no tickets and `false` otherwise. The Workboard exposes a `ready` guard that `can` consumes: human drivers may only request new commands when the board is presently ready, but dominoic effects spawned by existing requests can still add tickets while other work is outstanding.

## Concerns discussed
* Too many change events used to bleed through, but that noise has been tamed by the earlier work. The remaining concern is not the emissions themselves but knowing when every upstream trigger has finished running its downstream plumbing so that external subscribers can act confidently once the aggregate work finishes.
* There are multiple actors that can trigger reconciliation: Supabase table touches from any player, the current player issuing a move or do-over, timer catch-up ticks, and downstream dominoes that fire once another request resolves. Each of them needs to push work onto the Workboard so it is accounted for, whether the trigger is direct or indirect.
* The CLI can’t make safe exit or command sequencing decisions without knowing whether a request still awaits resolution. Right now there is no definitive signal that all pending requests have settled.
* Having a shared counter/registry of outstanding requests creates that signal. Once the register reads zero, the CLI can confidently say “no work remains in flight,” even if some intermediate atoms are still recalculating.
* The Workboard offers a `ready` guard that `can` uses to prevent new human-driven work until the outstanding work drains. Downstream dominoes, however, may still add tickets to a non-empty board; they do not get the same guard because they only run once the controlling request has started.

## Goals for this work
1. **Catalog async entry points.** Enumerate every place that reaches outside the process (`getTouches`, `getPerspective`, `getLastMove`, `move`, `undo`, timer-driven `r.forward`, etc.) and document how each one contributes to the ongoing state transitions.
2. **Build the request tracker.** Introduce a counter/registry that increments before launching each request and decrements in a `finally`-style handler so that success, failure, or cancellation all return the counter to the correct value.
3. **Expose the tracker state.** Surface the counter (or a derived boolean like `noOutstandingRequests`) inside the derived `$state` so external consumers and CLI instrumentation can read it without probing the internals.
4. **Protect against rapid repeats.** Ensure the tracker cannot be fooled by timer ticks or overlapping wake-ups—if a timer tick fires while the previous tick’s work is still running, the counter must not momentarily jump or leak (use idempotent guards or dedupe keys if necessary).
5. **Validate via CLI.** Instrument `src/libs/reel/cli.js` so it observes the tracker, logs its value alongside `$reel` snapshots, and only considers the system ready to exit when the register reaches zero. That logging will prove the tracker and the CLI heuristics agree.
6. **Make `$ready` a derived signal from `$workboard`.** The existing `can` helper demonstrates the shape the Workboard must support: wrap async actors in a block that requests work at the start and clears the ticket in a `finally`-style handler regardless of resolve or reject. `$workboard` tracks requests from table touches, user commands, timer ticks, and chained dominoes, while `$ready` simply mirrors whether the Workboard is empty. `$error` continues to capture the most recent failure so even rejected work can settle the Workboard without being retried automatically.

## Workboard class blueprint
We are merging the earlier ideas into a single Workboard abstraction anchored by a `$workboard` atom, a `$ready` derived signal, and the existing `$error` sink:

1. The `$workboard` atom is the pure observable state representing every in-flight request. It maps internal numeric ids to descriptive entries (e.g. `{0: {key, startedAt}, 1: {...}}`). When the object has no keys, nothing is outstanding and the system is ready—the board is empty, and both the filter on `$workboard` and the derived `$ready` should report that fact.
2. The Workboard helper/class is constructed with the `$workboard` atom, the `$error` atom, and any metadata needed to describe the actors. It exposes `register(key, op, blocking = false)` to describe the operations it can run and `request(key, ...args)` to actually invoke them. `register` stores the promise factory (`op`) along with the `blocking` flag (`true` for human-driven moves/do-overs) so `request` knows whether the caller should wait for `$ready` before it starts.
3. `request(key, ...)` replaces the old `can` guard. It checks the Workboard’s derived `ready` state for blocking operations, adds a new ticket (incrementing the internal counter) before invoking the registered `op`, and removes the entry in a `finally`-style handler regardless of resolve or reject. Reject still records the error via `$error`, but it also returns the board to readiness by dropping the ticket; there are no automatic retries baked into the manager.
4. Any actor—including table touches, timer ticks, perspective fetchers, and domino-triggered follow-ups—routes work through the same contract so every request automatically appears on the shared board. Dominoes can add tickets even while other work remains, but blocking operations will only run once the board is empty.
5. This design keeps the current shape of the system: we still issue commands via the same helpers (`move`, `undo`, `getPerspective`, etc.), but they now flow through the Workboard class so the busy count, derived `$ready`, and `$error` sink stay centralized while the rest of the code continues to look like “add the ticket, let the Workboard manage it, and then observe readiness.”
